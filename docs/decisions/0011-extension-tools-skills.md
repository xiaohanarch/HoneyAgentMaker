# ADR 0011 扩展标品 Agent、工具中心与技能编辑器

状态：已采纳（P6，2026-10-16）。

## 背景

P6 要在 Studio 里补上三块能力：租户在标品 Agent 声明的扩展点上做扩展（故事 B），工具中心（从 BO API 的 OpenAPI 生成工具、登记 MCP Server 并审批），以及技能编辑器（步骤表单、流程图、单独测试）。主提示词 5.2 到 5.4 节规定了三层资产和扩展点的组装规则，8.3 节要求未审批的 MCP Server 不能用在生产环境，第 10 节要求扩展发布前同时跑标品的公开评测集和扩展自己的评测集。

需要决定的是：扩展发布后什么时候对租户生效，评测时遇到确认点怎么办，复制为租户 Agent 时能复制什么，MCP 审批放在哪一层检查，技能怎么在不建 Agent 的情况下单独测试，以及演示剧本怎样区分扩展前后。

## 决策

### 扩展草稿与有效定义预览

扩展和新建 Agent 共用工作区草稿（`studio_drafts`，kind 为 AgentExtension），命名空间是 `tenant.<租户>.extensions`。本租户已有该标品 Agent 的已发布扩展时，新建扩展从它开始编辑，名称沿用，避免同一个标品出现两个并列的扩展。编辑器按扩展点分页（指令追加、工具、技能、知识、钩子、确认点、模型档位），每页保存时服务端只改这一页对应的字段；标品没有声明的扩展点在界面上锁住，即使改 YAML 写进去，静态检查也会以 extension-point-declared 报错。

有效定义预览用租户视角组装：草稿以叠加方式（ADR 0010 的 `OverlayResolver`）交给组装器，叠加里的 AgentExtension 替换同名的已发布扩展，其他已发布扩展照常参与。标品指令在租户视角下是占位块，接口返回 `{"$redacted": true, label, digest}`，界面锁住显示；租户追加的片段标出来源，界面高亮。

### 发布即生效

扩展没有 dev、test、prod 的晋级：扩展发布后，本租户的用户下一次运行该标品 Agent 时就按扩展后的定义运行。理由是扩展本身不能削弱标品（只能追加、只能更严格），而且发布前已经强制跑过双评测；再加一套环境会让“标品升级后扩展是否仍然有效”的判断变复杂。代价是扩展没有灰度，发布错了只能再发布一个修正版本。

发布依次检查：扩展评测集存在（否则 409 `NO_EVALS`）、静态检查没有错误（`LINT_FAILED`）、用到的租户 MCP 工具来源都已审批（`MCP_NOT_APPROVED`）、同一内容的评测已经通过，没有就当场跑一遍（不通过为 `EVALS_FAILED`）。通过后扩展和它的评测集一起写入注册中心并签名，写 `studio.extension.publish` 审计。

### 发布前的双评测

评测同时运行标品 Agent 的公开评测集和扩展评测集，被测对象都是“标品叠加扩展草稿”，每个评测集按自己的最低通过率判断，全部通过才算通过。评测结果按内容哈希记录，与 ADR 0010 的评测门禁同一套。评测引擎归 P8，P6 只通过 `EvalRunner`、`EvalRunStore` 的公开接口调用。

评测运行里遇到确认点一律拒绝，最多拒绝 5 次。这样评测不会真的发出 IM 通知或写入业务数据；同时“调用了 notify_im”这类断言仍然成立，因为工具调用在确认点之前已经发起并记录。扩展评测集初稿按扩展内容生成：为新增的每个工具加一条 calledTool 断言，再加一条按追加指令写的裁判断言。

为了让扩展评测集能直接引用技能或工作流的结构化结果，不变量断言里的 CEL 变量增加了 `result` 作为 `output` 的别名（`EvalRunner` 的一处小改动，已与 P8 的评测引擎约定）。

### 复制为租户 Agent

复制为租户 Agent 生成一份 `tenant.<租户>.agents` 下的 Agent 草稿，名称加 `-copy`，标签 `copiedFrom` 记录来源版本。副本的指令是标品的公开版指令（`publicInstructions`），不含标品指令原文；约束只复制规则编号，自由文本约束在租户视角下是占位块，不复制。工具、语义包、渠道、写策略、确认点、模型档位照常复制，评测集不复制，副本要自己生成。接口同时返回提示：副本归本租户所有，不再随标品升级。副本之后走新建 Agent 的同一套流程（ADR 0010）。

### 工具中心与 MCP 审批

工具中心列出本租户可见的工具来源和技能，带写级别和被哪些资产引用。BO 工具导入读取 DemoERP 的 `/bo/v1/openapi.json`，复用 `ImportBoTools.fromOpenApi` 生成入参 schema，生成的工具来源用连接别名 `DEMO_ERP`，不写地址。MCP 登记时平台用 MCP Java SDK 连到连接别名对应的服务列出工具，开发者逐个标写级别后生成工具来源资产，同时新建一条审批记录（`mcp_approvals` 表，迁移 V5）。只有租户管理员能批准或拒绝，写审计。

审批检查放在发布和晋级的门禁里，不放在工具网关：`McpGate` 作为额外的 prod 门禁注册到 `StudioReleases`，Agent 晋级 prod 和扩展发布时检查用到的租户 MCP 工具来源是否都已审批。标品的 MCP 工具来源由厂商审核，不在租户审批范围内。运行时实际调用 MCP 工具由工具网关负责，工具网关归 P7。

### 技能单独测试

技能编辑器的单独测试不要求先建 Agent：平台临时组装一个测试 Agent（`tenant.<租户>.agents/skill-tester`，只挂这一个技能），和技能草稿一起叠加，以测试用户的身份直接执行技能工具（`RuntimeService.testTool`），不经过模型。技能引擎在每个步骤的 span 上记录 `eab.step.input`、`eab.step.output`（截断到 2000 字），编辑器从追踪里取出每一步的输入输出和状态。技能里的确认步骤会让运行挂起，单独测试返回 `confirmation` 状态，不继续执行。

### 启动入库与演示剧本

启动时除连接外，租户的工具来源（`tools`）和工作流（`wf`）也随平台入库，因为扩展要引用 `tenant.t001.tools/notify-im` 和 `tenant.t001.wf/create-followup-task`。租户的扩展本身不预置，故事 B 由开发者在 Studio 里完成。

脚本化模型的剧本增加可选的 `match.tools`：只有这些工具在本次运行里可用时才匹配，带工具条件的剧本优先。故事 B 的剧本（`demo/scripts/story-b.yaml`）要求 `notify_im` 可用，所以扩展发布前仍走标品的剧本，发布后自动切到扩展后的剧本，断网也能演示扩展前后的差别。

## 后果

- 扩展发布即生效，演示路径短；没有灰度，标品升级时扩展是否仍然有效由 P8 的升级影响分析处理。
- 评测拒绝所有确认点，评测不会产生副作用，但也测不到“用户确认之后”的那部分行为，这部分靠私有环境里的人工测试。
- MCP 审批只在发布和晋级时检查，开发者在私有环境里仍然可以试用未审批的 MCP 工具。
- 命令行写入注册中心（`eab push`）在 P9 加入，走同一个注册中心接口，租户写不进标品命名空间的规则已经由 REST 接口覆盖。
