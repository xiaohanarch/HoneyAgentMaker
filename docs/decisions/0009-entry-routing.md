# ADR 0009 统一入口的路由：BM25 召回，嵌入检索预留接口

状态：已采纳（P4，2026-10-16）。

## 背景

主提示词第 9 节要求统一入口做两级编排：入口先选岗位助手，岗位助手再在自己的成员 Agent 里选，每一级都是“候选召回、权限过滤、模型决策”，置信度低时请用户澄清，找不到合适的能力时给出提交扩展需求的入口。能力目录在演示里只有十几个条目，但真实环境里一个租户可能有上百个岗位助手和 Agent，召回的方式需要能替换。

演示必须断网可用，路由结果还要能写进测试和验收脚本，同一句话每次路由到同一个 Agent。

## 决策

能力目录由 `dev.eab.runtime.routing.Catalog` 从注册中心里本租户可见的已发布资产生成。每个条目有类型（岗位助手、Agent、导航场景）、显示名、路由说明、示例话术，Agent 还合并它挂载的语义包里、它的工具能完成的典型任务。导航场景（打开供应商详情、打开采购订单）是平台内置的两个条目，不是资产。

召回用 BM25：每个条目的路由说明和示例话术各作为一段文本，按问题检索，条目取分数最高的那段，保留前五个候选。召回接口是 `Router.Retriever`，以后换成嵌入检索只需要另写一个实现，再在平台配置里替换。BM25 的分词沿用文档检索的做法（中文按字的二元组，英文和数字按词），不依赖外部服务。

权限过滤在召回之后、决策之前：岗位助手走鉴权点 1（策略引擎的 entry 规则，裁决写入审计）；Agent 要求用户在 ERP 里至少有它声明的一项 BO 操作的权限；导航场景不过滤，打开的页面本身按数据权限展示。被过滤的候选保留在路由说明里，并写明原因。

决策由 `Router.Decider` 完成，有两种实现：

- 按分数决策：选分数最高的候选，置信度是它的分数占前两名分数之和的比例。脚本化模型下使用，结果确定。
- 模型决策：把候选的名称、说明和召回分数交给 fast 档位的模型，要求输出所选候选、置信度和一句理由。模型调用失败或输出无法解析时退回按分数决策。配置了真实模型时使用。

阈值：召回分数低于 1.0 视为不匹配；置信度低于 0.6 且有两个以上可用候选时澄清，给出前两个候选；没有可用候选时是能力缺口。

路由的候选、分数、过滤原因、决策理由写进本次运行追踪的 routing span，并作为 routing 事件推给前端的路由说明面板。导航、澄清、能力缺口三种不交给 Agent 的结果也记一次运行（Agent 记为 `platform/router`），这样它们同样有追踪可查。

## 后果

- 断网时路由完全确定，测试和验收脚本可以断言路由到哪个 Agent。
- BM25 对同义改写不敏感，例如“到货晚了多少”不容易匹配“逾期交付率”。缓解办法是在资产的示例话术里多写几种说法；接入嵌入检索后这个问题会小很多。
- 两级路由多了一次召回和过滤，脚本化模型下耗时在十毫秒以内；用模型决策时每级多一次 fast 档位的调用。
- 能力目录每次提问时从注册中心重新生成，资产发布后立即生效。条目多了以后可以按租户缓存，在资产入库时失效。

## 真实模型下的验证（2026-10-16）

用 OpenAI 兼容协议接入 glm-5.3-flash 后，四种交互模式都能跑通。模型决策在每一级给出理由，置信度在 0.95 到 0.98 之间，选择与按分数决策一致；事务型话术里模型调用写工具，平台弹出 L2 确认卡片，确认后提交交期变更单；张敏和李强同问逾期交付率，李强得到只能查看华南数据的说明。

同时暴露出三个问题，前两个已修复：

- 路由决策直接调用 `ChatModel` 时传入通用选项，OpenAI 模块拒绝，决策一直静默退回按分数。现在经 `ChatClient` 调用，并有对模拟厂商服务的回归测试。
- 推理模型把输出上限用在推理上，正文为空。输出上限改为可配置，正文为空时运行以 MODEL_EMPTY_REPLY 失败。
- 单次模型调用耗时 10 到 200 秒不等，主要来自网关排队；库存经营分析 Agent 每轮只调用一次计算器，八轮用满仍没有结论。Agent 指令和工具返回量的调优放到 P8，用评测集衡量效果。
- 模型自己逐行统计时结果不稳定：同样的 172 条交付记录，两次运行数出的第三季度逾期行数分别是 43 和 77。按口径的计数和比率应该由工具聚合后返回（BO API 或语义层），模型只解释结果；这一项和上一项一起放到 P8。
- 模型请求的超时和重试原先沿用 Spring AI 厂商模块的默认值（60 秒、重试 3 次），推理模型处理大输入时单次常超过 60 秒，被反复取消。现在可以配置，默认 300 秒、重试 1 次。
