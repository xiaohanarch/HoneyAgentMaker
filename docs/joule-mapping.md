# 与 Joule Studio 的能力对应

本系统是参照 SAP Joule Studio 公开资料的概念演示，与 SAP 没有任何授权或从属关系（声明见 README）。本文逐项列出本系统能力与 Joule、Joule Studio 公开能力的对应，供对照讲解和评估参考。对应到主题和机制层面，不是逐字对照；`demo/DEMO.md` 里两个映射列（对应 Joule 能力、对应白皮书主题）的完整依据在这里。「出处」指 `docs/brief/01-Joule-Studio调研摘要.md` 的节号，原始链接都在那篇摘要的「资料来源」里。

## 开发态

| 本系统能力 | Joule 与 Joule Studio 的对应能力 | 出处 |
| --- | --- | --- |
| 从一句话意图新建 Agent：13 步向导，每一步 AI 先给推荐 | IVJ 演示的建模流程：一句话描述目的、起名并自动补全、关联业务流程、连接其他 Agent、添加数据产品、装配技能、定义触发方式、设置渠道、编写指令和约束、选择推理模型、测试、部署，每一步 AI 先给推荐、用户只做确认 | §2 |
| 意图驱动的方案生成：意图澄清、fit-gap、需求摘要、技术规格、资产草稿、评测集草稿六张卡 | 意图驱动开发六阶段（意图、需求、技术规格、代码生成、测试与评测、部署）；用一句话需求构建完整方案的演示 | §5、§6.3 |
| 扩展需求闭环：统一入口提交扩展需求，自动附带相关的业务对象与规则，开发者生成方案、交付后通知提出人 | 业务用户把推荐转成开发需求，Knowledge Graph 自动把截止日期、供应商、审批规则附在需求上，开发者收到通知、一键生成扩展，业务用户收到上线通知 | §6.4 |
| 扩展标品 Agent：七类扩展点（追加指令、加工具、加技能、加知识、挂钩子、加确认点、选模型档位） | Agent Extension：加技能、加指令、加数据字段、挂钩子，核心逻辑不允许改；North Star 的四种扩展方式（通过 MCP 加工具、加技能、挂前后置钩子、注入指令） | §3、§7.7 |
| 复制为租户 Agent：复制后归租户所有，不随标品升级 | 想改标品核心就自建一个 Agent，不再享受标品升级 | §3、§8 |
| 私有环境测试：草稿叠加在已发布资产之上，可选测试用户的身份 | 测试时选择私有环境和连接目标，Timeline 里逐节点展开，点技能名看输入输出 | §7.3 |
| 评测集：从语义包的已验证任务生成初稿，发布前作为门禁 | AI 生成测试用例、验证、审查结果；测试用 Gherkin 对话测试并设最低通过率 | §6.3、§7.4 |
| 环境晋级：dev、test、prod，晋级 prod 有门禁 | 先在项目里测试，再部署到共享环境，最后发到生产 | §3、§7.3 |
| 技能与工作流：确定性步骤流程，流程图编辑，可单独测试 | Skill 是确定性的单一任务单元；n8n Workflow 是内嵌的可视化多步骤自动化 | §3 |
| 专业代码通道：eab CLI 与 Studio MCP Server 指向同一条草稿链路，工程导出与 init 同构 | Joule Studio CLI 配合编码 Agent 开发；通过 MCP 把开发技能加载进编码 Agent；低代码与专业代码产出同一规范制品 | §5、§7.2 |
| 代码 Agent SDK：Java 代码实现业务逻辑，以 A2A 对外服务 | Custom Agent Runtime：代码型 Agent，专业代码路线 | §7.2 |
| 资产只写连接别名，地址与凭据按环境绑定在 Connection 资产里 | 能力包只写 system_aliases，真实地址和认证由各环境的 Destination 决定，同一个包跨环境部署 | §7.4 |
| 能力目录条目带场景描述与示例话术，作为路由依据 | Scenario：自然语言描述加示例句（路由依据）加目标函数 | §7.4 |

## 接入与运行

| 本系统能力 | Joule 与 Joule Studio 的对应能力 | 出处 |
| --- | --- | --- |
| 统一入口：最终用户只面对一个入口 | Joule 是 SAP 产品的统一入口 | §4、§7.1 |
| 两级编排：入口先选岗位助手，岗位助手再在成员 Agent 里选；每一级是召回、权限过滤、决策 | 入口路由到岗位助手，助手再编排一组 Agent；编排器同时参考 Scenario Catalog、Knowledge Catalog、用户上下文，拼成增强请求交给大模型 | §6.1、§7.1 |
| 岗位助手（Assistant 资产，编排一组 Agent，带 KPI） | Joule Assistants 按岗位划分，负责理解业务上下文、决定调哪些 Agent；每个 Assistant 带预期 KPI | §6.1、§6.2 |
| 标品 Agent（厂商层资产，随产品交付） | Joule Agents 负责执行，跨系统完成多步任务；首批按领域组织成自治域 | §6.1、§6.2 |
| 四种交互模式：事务、导航、信息、分析落在不同 Agent 上 | Joule 的四种能力模式：事务型、导航型、信息型、分析型 | §7.1 |
| 三类执行器：技能执行器（确定性）、声明式 Agent、代码 Agent | 三种运行时：Joule Execution Runtime（确定性）、Managed Agent Runtime（内容型）、Custom Agent Runtime（代码型） | §7.2 |
| 业务事件触发：以登记过的委托受托运行 | Assistant 的三种触发方式：人触发、系统触发加人工把关、完全自主运行 | §6.2 |
| A2A 出站：远程 Agent 挂到岗位助手（agent-request），或被平台 Agent 当工具调用 | BYOA：任何框架写的 Agent 实现 A2A Server，在 Joule 建 Scenario 挂 agent-request 类型的 Dialog Function | §4、§7.5 |
| A2A 入站：外部平台带用户令牌调用平台的岗位助手和 Agent | A2A 双向：外部 Agent 经 Agent Gateway 发现并调用 Joule Agent | §4、§7.5 |
| 多轮续接与超时转异步：contextId 续问；60 秒超时转异步，结果回调到通知区 | 多轮靠 contextId 与 taskId 写入跨轮变量；同步 60 秒超时，异步先返回 working、完成后经回调推送 | §7.5 |
| 子 Agent：Agent 把另一个 Agent 当工具调用 | Sub-agent：Agent 可以把另一个 Agent 当作工具调用 | §3 |
| Agent 卡片：远程 Agent 登记时读取 Agent Card（技能、交互模式、认证方式） | 新 Agent 在 Agent Hub 登记后自动开通身份，并带着 Agent Card 注册 | §7.6 |
| MCP 工具接入：MCP Server 登记为工具来源，声明写级别，生产使用需管理员审批 | Tool 经 MCP Server 批量导入；AI Agent Hub 只放行经过验证的 MCP Server 进生产 | §3、§4 |
| 文档知识库：Markdown 知识源作为文档检索工具挂到 Agent 上 | Document Grounding：文档检索增强，给 Agent 补业务知识 | §3 |

## 身份与权限

| 本系统能力 | Joule 与 Joule Studio 的对应能力 | 出处 |
| --- | --- | --- |
| 双重身份：用户加 Agent，有效权限取交集 | 代表用户执行时，有效权限是用户权限和 Agent 权限的交集 | §7.6 |
| 四处鉴权：入口、Agent 交接、工具与 MCP 网关、BO API，越早拒绝越好 | 三层策略执行点：网关入口、Agent 交接前、应用侧 API 与工具调用 | §7.6 |
| 委托：用户把权限的一个子集授予 Agent 供受托运行，可撤销 | 用户可以把自己权限的一个子集授予 Agent，供无人值守执行 | §7.6 |
| BO API 与身份透传：平台只经令牌交换以用户加 Agent 的身份调业务接口，失败即拒绝 | 用户在应用里做不了的事 Joule 也做不了；身份透传漏配会静默退化成技术用户，是公开资料里点名的坑 | §7.5、§8 |
| 写操作四级（L0 到 L3），L2 写入前人工确认，付款过账类最高 L2 | 人工批准、审批门控；Agent 编辑器里关键决策默认开启人工介入 | §7.3、§8 |
| 监督层：写级别守卫、输出引用核对、行为异常告警，提示词之外的确定性防线 | 三层防御的监督层：输入校验、输出过滤、异常检测，高风险决策转人工 | §7.7 |
| 模型管道的脱敏与还原、输入输出过滤 | 输出经过安全、隐私、负责任 AI 的过滤后返回 | §7.1 |

## 治理与演进

| 本系统能力 | Joule 与 Joule Studio 的对应能力 | 出处 |
| --- | --- | --- |
| 追踪与审计：span 树按查看者裁剪，审计按用户、Agent、工具、单据查询和反查 | 持久化决策轨迹：当时知道什么、考虑了哪些选项、选了什么、结果如何；SOX 兼容的日志 | §5、§7.7 |
| 评测门禁：发布与晋级要求同一内容的评测通过 | 评测作为门禁；评估分技术指标、流程 KPI、业务结果三层 | §5、§7.7 |
| 升级回归：标品发布新版本时用依赖它的租户扩展的评测集回归 | 标品升级前回归 | §8 |
| 经验回流：用户纠正的结论经管理员审核写入租户语义包，所有 Agent 立即生效 | Company Memory：Agent 处理例外的方式回写成 process atom，人可以审核和修改规则，所有 Agent 立即生效 | §6.2 |
| 语义包：业务对象、关系、指标、规则、已验证任务 | Knowledge Graph 四层：API 与服务元数据、业务语义、数据产品元数据、客户扩展 | §7.7 |
| 治理中心：运行量、耗时、费用、确认次数、KPI 趋势 | AI Agent Hub：目标完成率、工具调用正确率、根因追踪、人工介入频率 | §5 |
| 方案包：租户资产编译成带签名的部署单元，按环境部署 | Solution 是部署单元，作为整体部署、共享生命周期 | §7.7 |
| 三层资产可见性：租户永远看不到标品指令原文 | 标品由厂商托管，客户看不到原始提示词；扩展是独立制品，运行时叠加 | §8 |

## 本系统自建的部分

架构视图（按运行回放点亮组件）和演示控制台（重置、故事起点、触发事件、模拟升级）是为了让架构师和管理者在 15 分钟内看懂机制而自建的讲解工具，Joule 公开资料里没有对应物。脚本化模型（断网演示）、演示完成态快照、30 天模拟历史同样是演示需要。此外有一批刻意不同的取舍，记录在 `docs/decisions/` 的 ADR 和需求文档 `docs/brief/02-主提示词.md` 里，例如资产三层命名空间与签名发布、运行日志重放式挂起恢复、租户扩展不经环境晋级即时生效。
