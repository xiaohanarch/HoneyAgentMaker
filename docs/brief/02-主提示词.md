## 1. 背景与目标

### 1.1 背景

我们有一套自研的多租户 ERP（下文用 DemoERP 指代它的模拟版本），正在建设 ERP-AI 技术架构。架构白皮书里规划了一个类似 Joule Studio 的开发平台，暂定名 ERP Agent Builder。它需要同时服务两类开发者：

- ERP 厂商自己的研发团队，用它开发随产品交付的原生 Agent（下文称标品 Agent）；
- 租户（客户）和生态伙伴，用它在标品之上扩展 Agent、新建 Agent，或者把在其他框架开发的 Agent 接进来。

不管 Agent 从哪里来，最终用户只面对一个统一入口。

### 1.2 这个演示要达成的目的

给架构师和领导看，让他们在 15 分钟内理解这类产品是什么、怎么用、背后的架构机制是什么，并能据此讨论我们自己的 Agent Builder 应该怎么建。所以：

- 可看性优先于完备性。每一个机制都要在界面上"看得见"：路由决策、权限裁决、扩展的组装结果、评测结论、审计记录，都要有可视化。
- 架构要真实。不能只是做几个假页面。核心机制（资产分层组装、身份透传与四处鉴权、A2A/MCP 互通、评测门禁）要真正实现，代码可以作为我们自建平台的参考原型。
- 开源。代码里不出现任何公司内部信息，不使用 SAP 的商标、Logo 和产品名作为本系统的名字。

## 2. 范围与非目标

在范围内：统一入口（对话界面 + API）、编排与路由、Agent 运行时、开发态 Studio（低代码界面 + 专业代码 CLI + 供编码 Agent 使用的 MCP Server）、治理中心、模拟 ERP、模拟身份服务、两个外部框架 Agent 样例、演示数据与演示脚本。

不在范围内：真实的大规模性能、高可用、多机部署；真实的企业 IdP 对接；生产级的沙箱隔离（用进程内隔离和策略检查模拟，在文档里说明生产方案）；嵌入 n8n（n8n 的许可证不是 OSI 开源许可，本项目自带一个精简的工作流引擎，并预留 webhook 方式对接外部工作流引擎的适配器）。

## 3. 术语

| 术语 | 含义 |
|---|---|
| 统一入口 | 最终用户唯一的交互入口，对应 Joule。界面上叫"ERP 助手"，名字可配置 |
| 岗位助手（Assistant） | 按岗位划分的编排单元，例如采购助手、库存助手、财务助手。统一入口先路由到岗位助手，岗位助手再编排一组 Agent |
| Agent | 由大模型驱动、能规划并调用工具的执行单元 |
| 技能（Skill） | 确定性的单一任务单元，输入输出结构化，逻辑固定，不依赖大模型推理 |
| 工具（Tool） | 对一个后端能力的封装，来源可以是 BO API、MCP Server、技能、另一个 Agent |
| 语义包（Semantic Pack） | 某个业务域的 ERP 语义资产，描述业务对象、关系、指标口径、规则、Agent 指令、已验证任务、权限维度 |
| 扩展（Agent Extension） | 租户对标品 Agent 的增强，是独立制品，运行时叠加 |
| 远程 Agent（Remote Agent） | 运行在平台之外、通过 A2A 接入的 Agent |
| 扩展点 | 标品 Agent 声明的、允许租户叠加内容的位置 |
| 能力目录 | 所有已发布的 Assistant、Agent、技能、工具的登记表，是路由的依据 |
| Agent 卡片 | 能力目录里每个 Agent 的元数据，对外即 A2A Agent Card |
| BO API | 面向业务对象的 API，基于人的授权，带数据权限，严格版本兼容，是 Agent 调用业务的标准通道 |
| 评测集 | 一组带期望结论和失败条件的任务，用于上线门禁和升级回归 |
| 场景（Scenario） | 能力目录里的一条路由登记：自然语言描述、示例话术、指向的执行目标。发布 Agent 或技能时自动生成；接入远程 Agent 时生成一个指向 A2A 调用的场景 |
| 方案（Solution） | 部署单元。一个方案可以包含多个 Agent、技能、工作流、扩展，作为整体编译、发布、晋级、回滚 |
| 连接（Connection） | 资产里只引用连接别名，真实地址和认证方式按租户、按环境配置。对应 SAP 的 system alias 加 Destination |
| 私有环境 / 共享环境 | 开发者个人的测试环境，以及团队共用的 dev、test、prod 环境 |

## 4. 总体架构

### 4.1 与 ERP-AI 五层两翼架构的对应

系统按 ERP-AI 白皮书的五层两翼逻辑视图组织，每个模块都要能在"架构视图"页面上点亮对应位置（见 10.9）：

```
┌──────────────────────── 安全与治理（左翼） ───────────────────────┐ ┌──── 运营与运维（右翼） ────┐
│ ① 用户体验层   统一入口 Web、IM 渠道模拟、外部调用方（A2A 入站）   │ │ 链路追踪                    │
│ ② Agent 编排层 路由器、岗位助手、工作流引擎、人工确认、SoD 检查    │ │ 评测与门禁                  │
│ ③ 应用层       左：DemoERP 存量应用（BO API、事件）               │ │ 指标与成本                  │
│                右：标品 Agent、租户 Agent、远程 Agent；共享服务    │ │ 生命周期与发布              │
│ ④ 知识层       语义包、文档知识库、元数据服务（模拟）              │ │ 审计查询                    │
│ ⑤ 平台能力层   模型网关、MCP 网关、Agent 网关、Agent 运行时、记忆  │ │                            │
└────────────────────────────────────────────────────────────────┘ └────────────────────────────┘
        开发态：ERP Agent Builder Studio（低代码界面、CLI、Studio MCP Server）贯穿所有层
```

一条命令启动以下进程（本地开发用 `pnpm demo`，也提供 docker-compose）：

| 进程 | 职责 | 默认端口 |
|---|---|---|
| `platform` | 平台主服务：资产注册与组装、路由、Agent 运行时、模型网关、MCP 网关、Agent 网关、工作流引擎、治理中心 API、模拟身份服务 | 4000 |
| `studio-web` | 开发态 Studio 前端 | 5173 |
| `assistant-web` | 统一入口前端（也可以和 Studio 合并为一个前端的两个应用入口，由你决定） | 5174 |
| `demo-erp` | 模拟 ERP：BO API、Open API、业务事件、元数据服务 | 4100 |
| `ext-agent-py` | LangGraph 编写的外部 Agent，A2A Server | 4200 |
| `ext-agent-ts` | 用 A2A 官方 JS SDK 手写的最小外部 Agent | 4300 |
| `ext-mcp-server` | 一个第三方 MCP Server 样例（物流在途查询） | 4400 |

### 4.3 一次请求的端到端链路

这条链路要在"链路追踪"页面上完整可见：

1. 用户在统一入口提问，携带用户令牌。
2. 入口鉴权（鉴权点 1）：用户能否使用统一入口、能否使用目标助手。
3. 路由器结合能力目录（描述、示例话术、向量相似度）和大模型分类，选出岗位助手；岗位助手再选 Agent。路由结果和备选项、置信度都记录下来。
4. Agent 交接鉴权（鉴权点 2）：被调用的 Agent 是否允许被这个调用方调用。
5. 运行时按组装规则（第 5.4 节）把平台安全规则、标品定义、租户扩展组装成本次运行的有效定义。
6. Agent 规划，调用语义查询工具理解业务对象和口径，调用工具。
7. 工具网关鉴权（鉴权点 3）：这个 Agent 是否声明过这个工具；写操作是否需要人工确认。
8. 令牌交换：以"用户 + Agent"双重身份换取委托令牌，调用 DemoERP 的 BO API。
9. BO API 鉴权（鉴权点 4）：按业务权限和数据权限做最终裁决，返回结果时标明被过滤的范围。
10. 钩子执行（如有），结果返回用户；全程写审计。

## 5. 资产模型

整个平台的核心是一套声明式资产。所有资产都是 YAML 文件，可以在 Studio 界面里编辑，也可以用 CLI 拉到本地、放进 Git、再推回平台。界面和文件是同一份数据的两种视图。

### 5.1 资产种类

| kind | 说明 |
|---|---|
| `Assistant` | 岗位助手：成员 Agent 列表、路由描述、KPI 定义、触发方式 |
| `Agent` | 指令、约束、模型配置、工具、技能、子 Agent、知识源、语义包、触发器、渠道、记忆、写操作策略、扩展点声明、评测集引用 |
| `Skill` | 确定性流程：输入 schema、步骤（调用工具、数据转换、条件、人工确认、通知）、输出 schema；可设为"仅允许被 Agent 调用" |
| `ToolSource` | 工具来源：`bo-api`（从 DemoERP 的 OpenAPI 描述导入）、`mcp`（MCP Server）、`http`（任意 HTTP，需手工描述） |
| `SemanticPack` | 语义包，结构见 5.5 |
| `KnowledgeSource` | 文档知识库（上传的 Markdown、PDF 文本），本地向量检索 |
| `AgentExtension` | 对标品 Agent 的扩展，结构见 5.3 |
| `RemoteAgent` | 外部 A2A Agent 的登记：Agent Card 地址、认证方式、路由描述、允许的调用方 |
| `Workflow` | 工作流，供钩子和技能复用 |
| `EvalSuite` | 评测集 |
| `DevRequest` | 业务用户提交的开发需求，带自动附加的业务上下文 |
| `Solution` | 方案：列出包含的资产及其版本，是编译、签名、发布、晋级、回滚的单位 |
| `Connection` | 连接别名的定义；每个环境各有一份绑定（地址、认证方式、凭据引用），凭据不进制品 |

能力目录里的 `Scenario` 由平台在发布时从 Agent、技能、远程 Agent 的路由描述自动生成，Studio 里可以查看和调整描述。

`Agent` 的 spec 至少包含以下字段（字段名与 Joule Studio 编辑器对齐，便于观众对照理解）：

```yaml
spec:
  expertise: 面向采购经理，分析供应商表现并制定降价谈判策略
  instructions: |
    ...
  additionalContext: 语气专业、简洁，先给结论再给依据
  constraints: [PUR-R-007]              # 引用语义包规则，也可以写自由文本约束
  model: {profile: reasoning, temperature: 0.2}
  executionSteps:                       # 前置与后置步骤，确定性执行
    pre:  [{skill: vendor.pur.skills/load-user-purchasing-scope}]
    post: [{guard: platform/amount-threshold-check}]
  tools:
    - skill: vendor.pur.skills/rfq-lookup
    - agent: vendor.pur/supplier-performance-analyst
    - remoteAgent: tenant.t001.remote/supplier-risk
    - mcp: {source: tenant.t001.tools/logistics-mcp, tools: [track_shipment]}
    - documents: tenant.t001.kb/negotiation-playbook
    - builtin: calculator
  semanticPacks: [vendor.pur/procurement]
  triggers: [{type: assistant}]          # assistant / event / schedule / agent
  channels: [assistant-web, im]
  memory: {longTerm: true}
  writePolicy: {maxLevel: L2}
  routing:
    description: 制定和供应商的价格、质保、交期、付款条件谈判策略
    examples: [帮我准备和百润精密的降价谈判, 这个供应商还能谈下来多少]
```

### 5.2 三层资产与可见性

| 层 | 命名空间 | 谁能写 | 租户能看到什么 |
|---|---|---|---|
| 平台层 | `platform` | 平台管理员 | 安全规则的名称与说明，看不到全文 |
| 厂商标品层 | `vendor.*` | 厂商研发 | 名称、描述、扩展点说明、工具清单、版本说明；看不到指令原文、提示词、内部评测集 |
| 租户层 | `tenant.<id>.*` | 租户开发者 | 本租户全部内容，其他租户不可见 |

标品包发布时做签名（演示里用内容哈希加平台私钥签名模拟），运行时校验签名，签名不符拒绝加载。租户对标品资产的任何写请求在 API 层直接拒绝，并写审计。

### 5.3 扩展点与扩展制品

标品 Agent 在 `spec.extensionPoints` 里声明允许扩展的位置。演示至少实现以下五类：

| 扩展点类型 | 租户能做什么 | 不能做什么 |
|---|---|---|
| `instructions.append` | 追加业务指令和约束 | 覆盖或删除标品指令 |
| `tools.add` / `skills.add` | 增加工具或技能 | 删除或替换标品工具 |
| `knowledge.add` | 增加知识源或语义包 | 删除标品知识源 |
| `hooks` | 在 `beforeToolCall`、`afterToolCall`、`onResult`、`onFailure` 挂工作流或技能 | 修改标品工具的入参出参 |
| `approvals.add` | 增加人工确认点（只能更严格） | 放宽标品已有的确认要求 |

扩展制品示例：

```yaml
apiVersion: eab.dev/v1
kind: AgentExtension
metadata:
  name: anomaly-analyst-ext
  namespace: tenant.t001.finance
  version: 0.3.0
spec:
  target: vendor.fin/transaction-anomaly-analyst@^1.0   # 语义化版本范围
  instructions:
    append: |
      本公司规定：单笔金额超过 50 万元的异常，结论中必须给出责任部门。
  tools:
    add: [tenant.t001.tools/notify-im]
  hooks:
    onResult:
      workflow: tenant.t001.wf/create-followup-task
      when: "result.severity in ['high','critical']"
  approvals:
    add:
      - tool: tenant.t001.tools/notify-im
        policy: require-confirmation
  evals:
    suites: [tenant.t001.evals/anomaly-ext-smoke]
```

如果租户确实要改标品核心，提供"复制为租户 Agent"操作：生成一份租户命名空间下的副本（仅包含租户可见的部分，指令原文以"标品指令（不可见，运行时注入）"的引用占位，或者在演示中直接给出一份公开版指令，由你选择并写 ADR），副本归租户所有，界面明确提示"复制后不再随标品升级"。

### 5.4 运行时组装规则

运行时组装器（`packages/assembler`）是本项目最重要的模块之一，要有完整的单元测试。规则：

1. 指令按固定顺序拼接：平台安全规则（不可覆盖）→ 标品指令 → 标品约束 → 语义包的 agent_instructions → 租户追加指令 → 租户追加约束。每一段带来源标记，便于在追踪里回放。
2. 工具集合 = 标品工具 ∪ 租户新增工具。租户工具名冲突时拒绝发布。
3. 人工确认策略取最严格者。
4. 钩子按"标品钩子 → 租户钩子"顺序执行；租户钩子失败不影响标品主流程，但要记录并在结果里提示。
5. 模型配置：租户只能在标品声明的允许范围内选择。
6. 版本解析：扩展的 `target` 是版本范围，组装时解析到当前生效的标品版本，记录在追踪里。
7. 输出一份"有效定义"（effective definition），Studio 里可以查看（租户视角下标品指令显示为折叠的占位块）。

### 5.5 语义包

结构沿用 ERP-AI 白皮书语义层设计。每个语义文件分三类段：投影段只写对元数据的引用（`ref: erp.pur.Supplier@v1`），运行时实时从元数据服务取；增量段写元数据里没有的业务说明；原生段（metrics、agent_instructions、verified_tasks）只存在于语义文件。

```yaml
apiVersion: eab.dev/v1
kind: SemanticPack
metadata: {name: procurement, namespace: vendor.pur, version: 1.0.0}
spec:
  objects:
    - ref: erp.pur.Supplier@v1
      description: 供应商主数据
      fields:
        - ref: rating
          enumMeaning: {A: 战略供应商, B: 合格供应商, C: 观察期供应商}
    - ref: erp.pur.RFQ@v1
    - ref: erp.pur.PurchaseOrder@v2
    - ref: erp.pur.Delivery@v1
  relationships:
    - from: erp.pur.PurchaseOrder
      to: erp.pur.Supplier
      verb: 向…采购
      cardinality: many-to-one
      notes: 一张订单只对应一个供应商
  metrics:
    - name: overdue_days
      displayName: 交付逾期天数
      definition: 计划交付日期到实际交付日期（未交付则到今天）的自然日差，取订单行最大值
  rules:
    - id: PUR-R-007
      ref: erp.pur.rules.negotiation_eligibility
      severity: block
      remedy: 交付逾期超过 90 天的供应商，不建议发起降价谈判，应先处理交付问题
  agent_instructions:
    - 引用金额时必须带币种
    - 对供应商下结论时，说明依据的时间范围
  verified_tasks:
    - id: PUR-VT-001
      question: 百润精密最近一次询价的报价情况如何
      expected_conclusion: 列出询价单号、报价行数、最低报价与目标价差异
      fail_if: 编造询价单号
  permissions:
    filter_dimensions: [采购组织]
    inherit_from: pur.supplier.list
    disclose_filtered: true
```

平台提供一组语义查询工具，以 MCP 网关工具的形式暴露给 Agent：`semantic.describe_object`、`semantic.get_metric`、`semantic.find_rules`、`semantic.search`。Agent 只通过这组工具读语义，不直接读元数据服务。返回结果同时带元数据版本和语义包版本。

`verified_tasks` 一份资产三种用途：Agent 的调用示例、评测集用例、路由的示例话术。

## 6. DemoERP：模拟 ERP

### 6.1 业务范围

覆盖采购、库存、财务三个域，够支撑演示故事即可：

- 采购：供应商、采购组织、询价单（RFQ）与报价、采购订单与订单行、交付记录、合同条款（价格、质保、交期、付款条件）
- 库存：物料、仓库、库存余额、出入库流水、呆滞标识
- 财务：应付发票、付款计划、交易异常记录、会计期间与结账检查项

### 6.2 多租户与数据权限

- 两个租户：`t001 星海制造`（主演示租户）、`t002 远航电子`（用于证明隔离）。
- 用户与权限示例：

| 用户 | 租户 | 角色 | 数据权限 |
|---|---|---|---|
| 张敏 | t001 | 采购经理 | 采购组织：华东 |
| 李强 | t001 | 采购员 | 采购组织：华南 |
| 王芳 | t001 | 财务经理 | 公司主体：星海制造本部 |
| 陈工 | t001 | 租户开发者 | 无业务数据权限，有 Studio 权限 |
| 赵管理员 | t001 | 租户管理员 | 管理 Agent 授权与委托 |
| 厂商研发 | vendor | 标品开发者 | 无任何租户业务数据 |

- 种子数据量控制在可读范围：每个租户约 40 个供应商、200 张采购订单、500 条交付记录、100 种物料、30 条交易异常。数据要有故事性，例如供应商"百润精密"有一张逾期 120 天的订单，"华东"和"华南"的供应商数量明显不同。

### 6.3 API 谱系

DemoERP 同时提供两类 API，用来演示越权问题：

| API | 认证 | 授权 | 用途 |
|---|---|---|---|
| BO API（`/bo/v1/...`） | 委托令牌（用户 + Agent） | 业务权限 + 数据权限 | Agent 的标准调用通道 |
| Open API（`/open/v1/...`） | 客户端凭证（集成账号） | 只有租户级隔离 | 系统集成，演示中作为反面对照 |

BO API 规范要求（每个接口都要满足，并在 OpenAPI 描述中体现）：业务对象的增删改查和关键业务动作；面向 Agent 友好的描述（字段业务含义、枚举含义、示例）；结构化错误（错误码、原因、建议的下一步）；写操作支持业务幂等键；返回中标明数据权限过滤情况（`filtered: true, visibleScope: ["华东"]`）；版本号在路径中。

DemoERP 输出 OpenAPI 文档，平台的 `bo-api` 工具来源从这份文档自动生成工具定义。

### 6.4 元数据服务与业务事件

- 元数据服务（`/meta/v1/...`）提供对象、字段、枚举、规则清单、权限维度的定义，带版本。语义包的投影段从这里取。
- 业务事件：交付逾期、库存低于安全线、交易异常产生、结账检查失败。事件可以作为 Agent 的触发器（第 8.6 节）。提供一个"演示控制台"按钮手工触发事件。

## 7. 身份、鉴权与审计

按 ERP-AI 白皮书第 7 章的设计实现，这是演示 G6 的核心。

### 7.1 双重身份

- 每个 Agent 发布时获得独立身份（`agent:<namespace>/<name>`）。
- Agent 代用户执行时，有效权限 = 用户权限 ∩ Agent 声明的权限范围。
- 模拟身份服务（`platform` 内置，基于 `jose` 签发 JWT）提供：用户登录（演示里直接选用户）、客户端凭证、令牌交换（参照 RFC 8693，委托令牌里同时带 `sub`=用户、`act`=Agent）。

### 7.2 三种调用模式

| 模式 | 说明 | 演示方式 |
|---|---|---|
| 代用户操作 | 用户在线发起，委托令牌实时交换 | 统一入口对话 |
| 受托自主运行 | 事件或定时触发，使用事先登记的委托（委托人、范围、有效期、可撤销） | 交付逾期事件触发库存 Agent；租户管理员可以在治理中心撤销委托，撤销后再次触发会被拒绝 |
| 机机集成 | 客户端凭证，无人的身份 | 只能调用 Open API；平台禁止 Agent 用集成账号调用 BO API |

### 7.3 四处鉴权

鉴权点 1 入口、鉴权点 2 Agent 交接、鉴权点 3 工具与 MCP 网关、鉴权点 4 BO API。前三处由平台实现为统一的策略检查模块（`packages/policy`），策略可以用简单的 JSON 规则或嵌入 OPA 风格的规则，由你选择；第四处由 DemoERP 实现。每一次裁决（允许、拒绝、原因、命中的规则）都写入追踪和审计。

### 7.4 写操作分级与 SoD

| 级别 | 含义 | 默认策略 |
|---|---|---|
| L0 只读 | 查询 | 自动执行 |
| L1 出建议 | 生成草稿、建议，不落库 | 自动执行 |
| L2 需确认的写 | 落库前必须由有权限的人确认 | 在对话中弹出确认卡片，展示将要写入的内容 |
| L3 可自主执行的写 | 低风险写操作 | 需要租户管理员显式开启 |

工具定义里声明级别；付款、过账类工具最高只能到 L2。SoD：同一用户不能通过 Agent 既提交又审批同一张单据，在鉴权点 3 检查。

### 7.5 审计

每次调用记录：时间、租户、用户、Agent（含版本和扩展版本）、会话、调用模式、调用的工具、访问的数据范围、鉴权裁决、结果摘要。治理中心提供"这个动作是谁通过哪个 Agent 做的"反查。

## 8. 运行时

### 8.1 三类执行器，一个编排入口

参照 SAP 的三种运行时，平台有三类执行器，由同一个编排器调度：

| 执行器 | 承载 | 说明 |
|---|---|---|
| 技能执行器 | `Skill`、`Workflow` | 确定性，不调用大模型 |
| 声明式 Agent 执行器 | 用 YAML 定义的 Agent（提示词加声明式工具） | Studio 低代码做出来的都是这一类 |
| 代码 Agent 执行器 | 用代码写的 Agent | 演示里通过 A2A 调用独立进程中的代码 Agent；平台提供 TypeScript SDK，让代码 Agent 也能声明为平台资产并复用平台的工具网关和鉴权 |

低代码和专业代码产出同一种方案制品，低代码 Agent 可以"导出为代码工程"在 IDE 里继续开发，不维护两套体系。

### 8.1.1 Agent 执行

- 自研一个轻量的 Agent 循环（规划、工具调用、观察、结束），支持子 Agent 调用和远程 Agent 调用。不要引入重型框架作为平台运行时，保持源码可读，便于架构师阅读。
- 支持流式输出，前端展示思考步骤摘要（不是模型原始推理）、工具调用卡片、确认卡片、最终结果。
- 每一步产生追踪 span：路由、组装、模型调用、工具调用、鉴权裁决、钩子、人工确认。数据结构兼容 OpenTelemetry 语义，存本地数据库，可选导出 OTLP。

### 8.2 模型网关

- 统一接口，支持 OpenAI 兼容协议和 Anthropic 协议的提供方，通过环境变量配置。
- 模型档位：`fast`、`reasoning`、`judge`。Agent 定义里引用档位，不直接写模型名。
- 脚本化模型（`scripted` provider）是默认提供方。它根据演示剧本（`demo/scripts/*.yaml`）按用户话术和上下文匹配，产出确定性的工具调用和回复，保证断网时演示也能完整跑通。剧本未覆盖的输入，回退到一个基于规则的简单回复，并在界面上标注"脚本化模型"。
- 记录每次调用的 token 数和估算成本。
- 模型调用走一条可配置的处理管道（参照 SAP Orchestration Service 的设计）：提示模板、知识检索注入、敏感数据脱敏（例如银行账号、身份证号在发给模型前替换为占位符，返回后还原）、输入输出内容过滤。每个环节在追踪里可见。

### 8.2.1 监督层

提示词之外的第二道防线，全部是确定性逻辑：

- 写操作前的守卫：金额阈值、业务规则（来自语义包 rules）、SoD、写操作级别。守卫拒绝时 Agent 必须把原因告诉用户，不能绕过。
- 输出守卫：结论里引用的单号、金额必须能在本次运行的工具结果里找到，找不到则标记为"未经核实"（演示里用简单的字符串比对实现即可）。
- 行为异常检测：同一会话短时间内大量写操作、访问范围突然扩大等，触发告警写入治理中心。

### 8.3 MCP 网关

- 平台对 Agent 暴露的所有工具都经过 MCP 网关，包括 BO API 生成的工具、语义查询工具、外部 MCP Server 的工具、技能。
- 平台本身对外提供一个 MCP Server 端点，外部的 MCP 客户端（例如 Claude Desktop、Claude Code）可以在用户授权后使用租户允许的 ERP 工具。
- 接入外部 MCP Server 时，需要在治理中心登记并审批，未审批的不能在生产环境使用。

### 8.4 Agent 网关（A2A）

- 出站：平台内的 Agent 调用 `RemoteAgent`，作为 A2A 客户端，支持同步、流式、异步任务（push 通知回调）、多轮上下文（contextId / taskId 透传）。同步调用超时 60 秒，超时转异步。
- 入站：每个已发布且允许对外的 Agent 和岗位助手，都通过 A2A Server 对外暴露，提供标准路径下的 Agent Card。外部调用方必须带身份，入站请求同样经过四处鉴权。
- 使用 A2A 官方 SDK，协议版本以官方最新稳定版为准，写进 ADR。Agent Card 同时在 `/.well-known/agent-card.json` 和旧路径 `/.well-known/agent.json` 提供，兼容 SAP 样例使用的 0.3.0 版本客户端。
- 远程 Agent 的调用在能力目录里表现为一个场景，执行动作类型为 `agent-request`（命名对齐 SAP 的 dialog function 动作，方便观众对照）。多轮时由平台保存 contextId、taskId，远程 Agent 返回 `input-required` 时把追问展示给用户。
- 身份透传失败即拒绝：令牌交换失败、委托缺失、配置不全时，一律拒绝调用并给出明确错误，绝不退回到技术账号。为这条规则写专门的测试。

### 8.5 记忆

- 会话记忆：同一会话内的上下文。
- 长期记忆：按"租户、用户、Agent"三元组隔离，存用户偏好和确认过的事实；Studio 里可以查看和清除。

### 8.6 触发器与渠道

- 触发器：统一入口直接调用（默认）、业务事件、定时、被其他 Agent 调用。
- 渠道：统一入口 Web（默认）；IM 渠道用一个模拟的 IM 界面（`/channels/im`）演示，结构上预留 webhook 适配器。

### 8.7 工作流引擎

精简实现，支持步骤类型：调用工具、调用技能、调用 Agent、条件分支、并行分发、人工确认、通知、等待事件。工作流定义是 YAML，Studio 里用 React Flow 画成流程图（可视化 + 简单编辑即可，不追求完整的拖拽编辑器）。

## 9. 统一入口与路由

### 9.1 两级编排

统一入口 → 岗位助手 → Agent。也允许入口直接路由到某个 Agent（当能力目录里该 Agent 被标记为"可直达"时）。

编排器每次决策参考三类输入：能力目录（场景、技能、Agent 的元数据）、知识目录（文档知识库和语义包）、用户上下文（租户、角色、数据权限范围、当前所在的 ERP 页面、对话历史）。

### 9.1.1 四种交互模式

统一入口支持 Joule 的四种模式，演示时各准备一句话术：

| 模式 | 示例 | 实现 |
|---|---|---|
| 事务型 | "把 PO-2026-0117 的交期改到下月 15 号" | 技能或 Agent 调用 BO API，L2 确认 |
| 导航型 | "打开百润精密的供应商详情" | 返回 DemoERP 页面的深链接卡片（DemoERP 提供几张极简的只读页面） |
| 信息型 | "我们的降价谈判制度是怎么规定的" | 文档知识库检索，回答附引用 |
| 分析型 | "华东区本季度逾期交付率是多少" | 语义包指标口径 + BO API 聚合查询，回答附口径说明 |

### 9.2 路由算法

1. 候选召回：用能力目录里的路由描述和示例话术（含 verified_tasks）做向量相似度，取前 5。本地向量用一个轻量的嵌入方案（可以是本地小模型、或在没有模型时用 BM25 关键词召回），由你选型并写 ADR。
2. 过滤：去掉当前用户无权使用的候选（鉴权点 1）。
3. 决策：模型在候选里选择，输出理由和置信度；置信度低于阈值时向用户澄清，或给出两个选项让用户选。
4. 记录：路由决策、候选、分数、理由进入追踪。

统一入口界面上有一个可展开的"路由说明"小面板，演示时展开给观众看。

### 9.3 能力缺口与需求提交

当路由找不到合适的能力，或者 Agent 判断自身没有完成任务所需的工具时，统一入口给出"提交扩展需求"按钮（故事 E）。

## 10. 开发态：ERP Agent Builder Studio

### 10.1 首页

- 当前身份（厂商研发 / 租户开发者，可切换，用于演示两层视角）
- 我的项目、最近编辑、待处理的开发需求
- 入口卡片：从意图新建、扩展标品 Agent、接入外部 Agent、新建技能、导入工具

### 10.2 从意图新建 Agent（复刻 IVJ 演示流程）

向导式界面，左侧是步骤导航，右侧是表单，每一步顶部有"AI 推荐"区域，用户可以一键采纳或修改：

1. 描述目的：一句话意图
2. 命名：AI 生成名称建议、描述、头像（用 SVG 生成几何头像即可，不调用图像模型）
3. 业务流程归属：从流程目录（S2P 采购到付款、P2P 计划到生产、R2R 记录到报告等）推荐
4. 协作 Agent：推荐可调用的已有 Agent 和远程 Agent
5. 数据与知识：推荐语义包和知识源，可上传文档
6. 技能与工具：推荐技能和工具，标注每个工具的写操作级别
7. 触发器
8. 渠道
9. 指令与约束：AI 起草指令，约束可以从语义包的 rules 里勾选（例如 PUR-R-007）
10. 模型档位
11. 评测集：从语义包 verified_tasks 自动生成初始评测集，可补充
12. 测试：内嵌测试对话和链路追踪
13. 发布

每一步保存时，右侧同步显示生成的 YAML（只读预览，可切换到 YAML 编辑模式）。

### 10.3 意图驱动生成（AI 生成产物）

除了向导里的逐步推荐，提供"一键生成方案"：输入意图后，平台依次产出

1. 意图澄清：平台最多追问 3 个问题（附可选答案），把模糊意图补完整
2. 意图分析与 fit-gap：用能力目录、语义包、扩展点目录判断现有标品能力能满足多少，结论分三档（标品已满足，直接告诉用户用哪个；扩展标品即可；需要新建），给出匹配度分数和依据（命中了哪些语义对象、哪些已有能力）。这一步是"先复用、再扩展、最后新建"原则的落地
3. 需求摘要（PRD 精简版）：目标用户、场景、成功指标（含对业务指标的预期影响）、边界
4. 技术规格：要创建或复用的资产清单及其关系
5. 资产草稿：YAML
6. 评测集草稿

这些产物在界面上以卡片依次展开，每张卡片可以编辑、重新生成。生成过程使用模型网关；脚本化模型下按剧本输出。

### 10.4 扩展标品 Agent

- 标品 Agent 目录：展示租户可见的信息（描述、扩展点说明、工具清单、版本），指令原文不可见。
- 选择一个标品 Agent → 新建扩展 → 按扩展点类型分页编辑。
- "有效定义预览"：展示组装后的结果，标品部分折叠为不可展开的占位块，租户部分高亮。
- 发布前强制运行：标品自带的公开评测集 + 租户扩展的评测集。

### 10.5 接入外部 Agent（BYOA）

- 输入 Agent Card 地址，平台拉取并展示技能、输入输出模式、认证要求。
- 配置：路由描述、归属的岗位助手、允许的调用方、认证方式（演示里用平台签发的服务令牌）。
- 连通性测试：发一条测试消息，展示 A2A 请求与响应的原文（可折叠）。
- 发布后，外部 Agent 和原生 Agent 一样出现在能力目录里，统一入口可以路由到它。
- 页面上附"如何让你的 Agent 接入"说明，给出 Python（LangGraph）和 TypeScript 两个模板仓库路径。

### 10.6 技能编辑器

步骤列表 + 流程图预览。步骤类型同工作流引擎。可以单独测试（填入参数，查看每一步的输入输出）。

### 10.7 工具中心

- BO API 导入：读取 DemoERP 的 OpenAPI，勾选要生成的工具，自动带上描述、参数、写操作级别（从 OpenAPI 扩展字段读取）。
- MCP Server 登记：填地址，拉取工具列表，提交审批。
- 每个工具显示被哪些 Agent 使用。

### 10.8 测试与评测

- 测试对话：可切换"以哪个用户身份测试"，直观演示同一问题不同用户结果不同。
- 链路追踪视图：时间线 + 树形 span，点击 span 查看输入输出、鉴权裁决、组装后的有效指令（按可见性规则脱敏）。
- 评测运行：选择评测集运行，展示每个用例的通过与失败、失败原因。断言类型至少支持：调用了某工具、没有调用某工具、结果包含、结果不包含、数值区间、模型裁判（脚本化模型下使用确定性裁判）。评测断言优先用不变量（例如"列出的订单都属于华东"），少用依赖具体数据值的断言，避免数据一变全部失败。
- 评测集分层：冒烟集（全部用例 3 分钟内跑完）和完整集。

- 对话测试用例：除了评测集，再支持一种 Given/When/Then 风格的对话测试（参照 SAP `joule test` 的 Gherkin 用例），可以设"最低通过率"，因为大模型输出不完全稳定，按通过率判定而不是要求逐条全过。
- 私有环境测试：开发者在自己的私有环境里测试，选择用哪个连接绑定、以哪个用户身份；通过后才能发布到共享环境。

### 10.8.1 静态检查（lint）

发布前自动运行，结果显示在发布面板上：

- 场景描述唯一性和重叠度：与能力目录里已有场景的描述相似度过高时告警，避免路由冲突
- 资产里不得出现硬编码地址和凭据，只能引用连接别名
- 工具写操作级别必须声明
- 扩展只能使用目标 Agent 已声明的扩展点
- 引用的语义包规则、技能、工具必须存在且版本兼容

### 10.8.2 连接中心

管理连接别名，以及每个环境的绑定（地址、认证方式、凭据引用）。演示里预置 `DEMO_ERP`、`LOGISTICS_MCP`、`SUPPLIER_RISK_AGENT` 等别名。

### 10.9 架构视图

一个专门的页面，画出第 4.1 节的五层两翼图（SVG 或 React Flow）。演示时可以选中一次运行，图上依次高亮这次运行经过的组件，配合时间线回放。这个页面是给领导讲架构用的，要做得清楚好看。

### 10.10 专业代码通道

- CLI（`eab`）：`login`、`init`（从模板创建资产或外部 Agent 工程）、`pull`、`push`、`validate`、`eval`、`deploy`、`logs`。
- Studio MCP Server：把语义包查询、能力目录查询、扩展点目录、资产校验、评测运行、部署做成 MCP 工具，让 Claude Code、Cursor 这类编码 Agent 在本地开发时能拿到业务上下文并直接操作平台。
- 在 `docs/pro-code.md` 写一份用 Claude Code + Studio MCP Server 开发一个扩展的完整示例。

## 11. 治理中心（Agent Hub）

| 页面 | 内容 |
|---|---|
| 资产清单 | 全部 Assistant、Agent、扩展、远程 Agent、MCP Server、模型档位；按来源（标品、租户、扩展、外部）筛选；扩展与标品的血缘关系图 |
| 上架准入 | 发布审批队列。准入检查：评测门禁通过、工具写级别合规、MCP Server 已审批、签名有效 |
| 运行指标 | 每个 Agent 的目标完成率、工具调用正确率（评测口径）、人工介入率、失败 trace 数、P50/P95 延迟、token 与成本；岗位助手的 KPI 卡片 |
| 审计 | 按用户、Agent、工具、时间、结果查询；"谁通过哪个 Agent 做了什么"反查 |
| 委托管理 | 受托自主运行的委托清单，可撤销 |
| 升级回归 | 标品升级记录，以及每次升级对各租户扩展的回归结果 |
| 经验回流 | 用户在对话中纠正 Agent 的结论（点"结论有误"并写明原因），生成一条候选规则或候选 verified_task，进入审核队列；审核通过后写入租户层语义包的扩展部分，所有相关 Agent 下次运行即生效。对应 SAP 的 Company Memory 与决策轨迹，也对应白皮书"经验沉淀为语义资产，不沉淀为提示词"的原则 |
| 风险告警 | 监督层产生的异常行为告警 |

指标分三层展示，避免只盯技术指标：技术指标（目标完成率、工具调用正确率、延迟、失败率）、流程指标（例如谈判建议采纳率、异常处理时长）、业务结果（例如节省金额、库存周转改善，演示里用模拟数据）。

指标数据由运行时真实产生，再加一个"生成历史数据"脚本，灌入过去 30 天的模拟运行记录，让图表有内容。

## 12. 生命周期

- 每个资产有版本（语义化版本）、状态（草稿、测试中、已发布、已下线）、变更说明。
- 方案编译：把方案内的资产解析、校验、组装成一个不可变的方案包（例如 `.eabpkg`，内含清单、资产、内容哈希、签名），部署的对象是方案包。参照 SAP 把设计时制品编译成 `.daar` 再部署的做法。方案包与环境配置分离，连接别名在部署到具体环境时才绑定。
- 环境：每个租户有 `dev`、`test`、`prod` 三个环境，发布即在环境间晋级；支持回滚到上一个版本。
- 标品升级模拟：演示控制台里有"发布标品新版本"按钮，把某个标品 Agent 从 1.2.0 升到 1.3.0（例如修改指令和新增一个工具），平台自动对所有依赖它的租户扩展运行回归评测，在治理中心生成报告；有一个用例故意设计成升级后失败，演示通知租户的过程。
- 版本差异：两个版本的 YAML 差异对比视图（租户视角下标品指令不显示差异内容，只显示"已变更"）。

## 14. 技术栈与工程规范

| 方面 | 选择 |
|---|---|
| 语言与运行环境 | TypeScript（Node.js 22 LTS 或更新）为主；外部 Agent 样例用 Python 3.12 + uv |
| 仓库 | pnpm workspace 单仓，Turborepo 可选 |
| 后端 | Fastify 或 Hono（二选一，写 ADR），zod 做 schema 校验，从 zod 生成 JSON Schema 和 OpenAPI |
| 存储 | SQLite（better-sqlite3 + Drizzle ORM），零依赖启动；数据访问层抽象好，便于换 PostgreSQL |
| 前端 | React + Vite + TypeScript + Tailwind CSS + shadcn/ui；React Flow 画流程图和架构图；Monaco 编辑 YAML；TanStack Query |
| 协议 | A2A 官方 SDK（JS、Python）；MCP 官方 TypeScript SDK，传输用 Streamable HTTP |
| 身份 | jose 签发和校验 JWT |
| 测试 | Vitest 单元测试；Playwright 端到端测试覆盖全部演示故事 |
| 代码质量 | ESLint + Prettier；TypeScript strict |
| 许可证 | Apache-2.0 |

工程规范：

- 资产 schema 是单一事实来源，放在 `packages/spec`，前端、后端、CLI、Studio MCP Server 共用。
- 所有对外接口有 OpenAPI 描述。
- 不在代码中硬编码任何真实公司、真实人名、真实密钥。演示人名和公司名都是虚构的。
- 每个阶段更新 `docs/` 下对应文档，文档用中文。

## 16. 界面风格

- 企业软件的专业感，信息密度适中，留白克制。不要模仿 SAP Fiori 的视觉，不使用 SAP 的配色、图标和字体。
- 浅色为主，支持深色模式。
- 三类资产来源用一致的视觉标识区分：标品（锁形图标 + 一种主色）、租户（另一种主色）、外部（第三种主色），在所有页面保持一致。

## 17. 演示故事

演示由 `demo/DEMO.md` 描述，总时长约 15 分钟。演示控制台（Studio 右上角的隐藏菜单）提供：重置到初始状态、跳到某个故事的起点、触发业务事件、发布标品新版本、切换用户。

### 故事 A：从一句话新建价格谈判助手（G1、G4）

租户开发者陈工在 Studio 输入"帮采购经理制定和供应商的降价谈判策略"。走完向导：AI 推荐名称和头像、归属 S2P 流程、推荐协作的"供应商绩效分析 Agent"和外部"供应商风险舆情 Agent"、推荐采购语义包、推荐技能、默认触发方式、渠道选统一入口和 IM、约束里勾选 PUR-R-007（逾期超过 90 天不建议谈判）、模型选 reasoning 档。测试提示词："查一下百润精密最近一次询价，帮我出一份谈判策略"。追踪里可以看到 Agent 调用了询价查询技能、供应商绩效 Agent、外部风险 Agent，并且因为百润精密有一张逾期 120 天的订单，触发了约束，结论里先提示处理交付问题。运行评测集，通过，发布到 prod。

### 故事 B：增强标品 Agent（G2、G3）

陈工打开"交易异常解析 Agent"，看到只有描述、扩展点和工具清单，指令原文不可见。新建扩展：追加"单笔超 50 万的异常须给出责任部门"、增加 IM 通知工具（L2 需确认）、挂一个 `onResult` 钩子在高风险时自动创建跟进任务。打开有效定义预览，看到标品部分是锁住的占位块，租户部分高亮。发布前自动跑标品公开评测集和扩展评测集。在统一入口用王芳的身份问"本月有哪些高风险交易异常"，看到扩展生效，IM 通知前弹出确认卡片。

### 故事 C：接入 LangGraph 写的外部 Agent，并被外部反向调用（G5）

陈工在 Studio 输入 `supplier-risk-py` 的 Agent Card 地址，平台展示其技能，完成配置和连通性测试，发布。统一入口里张敏问"百润精密最近有没有什么风险"，路由面板显示选中了外部 Agent，链路里能看到 A2A 请求。然后运行 `client-demo` 脚本，模拟外部平台的 Agent 通过 A2A 调用平台的采购助手，治理中心的审计里出现这次入站调用，调用方身份清楚。

### 故事 D：Agent 不越权（G6）

1. 张敏和李强在统一入口问同一个问题"列出我们逾期超过 30 天的供应商"，结果不同，结果下方注明"已按你的数据权限过滤，可见范围：华东"。
2. 演示控制台切到"集成账号"模式，同样的问题走 Open API，返回两个采购组织的全部数据，界面用对照面板展示差异，说明为什么 Agent 必须走 BO API。
3. 张敏让采购助手"把百润精密订单 PO-2026-0117 的交期改到下月 15 号"，弹出 L2 确认卡片；确认后执行。张敏再让 Agent 审批这张变更单，被 SoD 拒绝。
4. 赵管理员在治理中心撤销库存 Agent 的受托委托，再触发"库存低于安全线"事件，Agent 被拒绝运行，审计里有记录。
5. 在审计页面反查"PO-2026-0117 的交期是谁通过哪个 Agent 改的"。

### 故事 E：业务用户提需求，开发者交付扩展（G7）

张敏问"百润精密这批货到不了，帮我从备选供应商里找有现货的下单"。采购助手发现没有"备选供应商下单"能力，给出"提交扩展需求"。张敏补一句"金额超过 10 万的必须人工审批"后提交。陈工在 Studio 首页看到新需求，需求里自动附带了相关语义对象、规则、张敏的原话。陈工点"生成方案"，平台产出意图分析、需求摘要、规格、扩展草稿（新增技能 + 工作流：有备选供应商就生成请购单草稿，没有就转给询价流程）和评测集。陈工审查流程图、运行评测、发布。张敏收到通知，重新提问，流程跑通，超 10 万时弹出审批。

### 故事 F：标品升级与治理（G1、G3）

厂商发布交易异常解析 Agent 1.3.0。治理中心自动生成升级回归报告：t001 的扩展有一个用例失败（因为标品新版把输出结构里的字段改名，租户钩子的条件表达式失效），租户收到通知。打开治理中心看资产清单、血缘图、各 Agent 三层指标、岗位助手 KPI。

再演示经验回流：王芳在统一入口指出交易异常解析 Agent 的一个结论不对（"这类跨期冲销不算异常"），治理中心出现一条候选规则，审核通过后重新提问，结论改变，追踪里能看到新规则来自租户语义包。

最后打开架构视图，选中故事 D 的那次运行回放，讲清五层两翼。

## 19. 交付顺序

## 20. 默认决策

以下问题如无特别说明，按默认处理：

| 问题 | 默认 |
|---|---|
| 统一入口和 Studio 是一个前端还是两个 | 一个前端工程，两个路由入口，顶部切换 |
| 标品指令在"复制为租户 Agent"时怎么处理 | 演示中给每个标品 Agent 准备一份"公开版指令"，复制时带上公开版，并在 ADR 中说明生产环境的选项 |
| 向量检索 | 先用 BM25 + 关键词，接口上预留嵌入模型；配了真实模型 Key 时可切换到嵌入检索 |
| 策略引擎 | 自写 JSON 规则引擎，规则可在治理中心查看 |
| 外部 Agent 的认证 | 平台签发服务令牌，A2A Agent Card 中声明 bearer 认证 |
| 国际化 | 中文为默认，预留英文资源文件，演示前只需完成中文 |
| 数据库迁移 | Drizzle migrations，种子数据脚本可重复执行 |
